# 桌面端播放拉取策略重设计

## 1. 结论

现有桌面缓存层把“回源连接”当成廉价、可取消、可并行的资源：默认 2 路、健康时升到 4 路，
每路 4–8 MiB 分段，另有按播放头预取的任务。百度网盘 CDN 的实际行为相反——**新连接建立要
5–15 秒，且对同一签名链接的并发连接非常敏感**。两者冲突后出现：

- 多个分段同时卡在 `connect`；
- 15 秒请求超时后分段失败，在缓存里留下**空洞**；
- 播放头读到空洞时再新建连接，又超时，形成“缓冲中 + 零速”；
- 用户拖动进度条会取消全部任务并重建，进一步放大连接数。

彻底的做法不是继续调超时，而是换成**单条主回源流 + 少量短探针**：
播放头顺序读到文件尾，读满预读窗口就暂停（TCP 背压），播放头移动就续读；
只有远离播放头的头部/moov 小范围读取才用独立探针。任何时刻最多 3 条连接，
不会产生并行分段留下的空洞。

## 2. 现场证据（2026-10-25 14:00）

```
14:00:30 jobs=[16777216-18874368:connect:0:3435ms,
               31457280-35651584:connect:0:3353ms,
               35651584-39845888:connect:0:3352ms,
               39845888-44040192:connect:0:3352ms]      ← 4 路同时建连
14:00:42 媒体分段失败 16777216-18874368 phase=connect error=TimeoutException
14:00:42 媒体分段失败 31457280-35651584 phase=connect error=TimeoutException
14:00:42 本地响应中止 offset=bytes=0- sent=true error=TimeoutException
14:00:51 用户 seek 到 199.6s（generation=1），再次新建 44–52MB 两路
14:01:03 媒体分段失败 46137344-50331648 phase=connect error=TimeoutException
14:01:29/34/39/44 连续 seek（generation 3/4/6/7），每次都重建连接
```

`stored=59074123` 说明磁盘上确实有约 59 MB，但它们是**分散的**：
16–18 MB、31–35 MB、44–50 MB 因超时失败留下空洞，播放头/解码器预读一旦碰到空洞就缓冲。
界面上看到的橙色缓存段由 mpv 的 `seekable-ranges` 与磁盘块按“字节/总时长”折算合并，
空洞边界和 VBR 码率会让它看起来“已经缓存”，实际缺块。这是观感问题，不是根因；
根因是并行分段 + 不可取消的连接 + 超时后留洞。

## 3. 为什么 Android / iOS 没有这个问题

| 维度 | Android（Media3） | iOS（CacheServer） | 桌面（现状） |
|---|---|---|---|
| 回源连接 | 播放 DataSource 单路顺序读，预取单独一路；Semaphore(4) 但播放优先 | 每个本地连接一条回源请求，最多 1 条按需 + 1 条推测 | 全局 2–4 路分段，播放与预取共用 |
| 取消语义 | OkHttp `Call.cancel()` 真正中止 TCP/TLS | `NWConnection.cancel()` 真正关闭 | Dart `HttpClient` 无法取消已排队的 `getUrl` |
| 空洞 | 播放请求优先占住自己的缓存洞，预取只填不冲突的洞 | 按需优先、推测可暂停/让位，绝不与播放抢同一段 | 分段失败即留洞，播放头后补再新建连接 |
| 背压 | `CacheDataSource` 洞锁 + 分段 DataSource | 本地在途 8MB 上限、40ms 节奏、播放位置窗口 | 只受 2GB 磁盘预算限制，预取可无限抢连接 |
| 缓冲显示 | Media3 精确字节缓冲位置 | RangeStore 精确磁盘区间 + 播放器已加载区间 | mpv 区间 + 磁盘区间平均码率折算，边界不准 |

关键差异不是“手机网络好”，而是**手机端只有一条按需主通路，且取消是真的**。
桌面端把播放和预取放进同一个并行调度器，再用一个取消不掉的连接池去抢 CDN 的建连配额。

## 4. 新策略：单流顺序缓存（Sequential Stream Cache）

### 4.1 拓扑

```
mpv ──Range──► 本地 HTTP 服务 ──► 磁盘块（命中直接返回）
                                   │ 缺块且靠近播放头
                                   ▼
                            主回源流（1 条，Range: start-）
                                   │ 顺序写盘、按窗口暂停/续读
                            短探针（最多 2 条，各 ≤4 MiB，头部/尾部专用）
```

### 4.2 规则

1. **主回源流只有一条**，从播放头所在的块边界开始，`Range: bytes=<start>-` 读到文件尾。
2. **读满预读窗口就暂停**：`stream.offset - consumed > prefetchBytes` 时不再读 body，
   依靠 TCP 背压让 CDN 停发；播放头前进或解码器缺块时恢复。不再用“新建连接”做预取。
3. **缺块处理**：
   - 缺块在播放头附近（≤8 MiB）：把主回源流重启到该块的缺失偏移；
   - 缺块远离播放头（头部、尾部 moov、格式探测）：启动最多两条 ≤4 MiB 的短探针（头部/尾部各一），
     不动主回源流。
4. **seek 不再取消任何任务**：`seek()` 只更新已消费位置；目标块命中磁盘就直接返回；
   未命中才由缺块逻辑重启主回源流一次。
5. **本地 HTTP 响应不再因 seek 中断**：去掉 generation 检查；客户端关闭连接自然结束。
6. **连接永不主动取消，只取消已建立的 body**：主回源流重启时关闭旧 body；
   待建立的 `getUrl` 留给它自己完成并丢弃，最多残留 1 条，连接池（4）不会耗尽。
7. **超时分层**：建连/响应头 25 秒；body 连续 12 秒无数据才重启；mpv
   `network-timeout` 提到 30 秒。任何一次重启都从最后已写入字节继续，不产生新洞。
8. **缓冲显示只认真实连续区间**：磁盘区间按块合并，末端预留 1 个块（约 2–5 秒）
   不标为已缓存；mpv 区间继续使用 `seekable-ranges`（它确实是可用的缓冲区间）。

### 4.3 与旧实现的差异

| 项 | 旧 | 新 |
|---|---|---|
| 并发连接 | 2–4 路分段 + 预取 | 1 条主流 + 最多 2 条短探针 |
| 预取方式 | 新建分段任务 | 同一条流继续读，窗口满则暂停 |
| 分段失败 | 留洞，播放头再补 | 从最后字节续读，不产生洞 |
| seek | 清空任务、generation++、断本地响应 | 只更新位置，命中即读盘 |
| 超时 | 3s/15s 取消重建 | 25s 建连、12s body，重启一次 |
| 连接池风险 | 僵尸请求可占满 4 个槽 | 最多 3 条，天然安全 |

## 5. 实施与验收

- 新实现 `SequentialMediaCache`，保持现有 `MediaKitEngine` 调用面（`open/localUrl/
  length/ranges/setConsumed/seek/networkSpeed/close`）。
- 回归用例：单流顺序、窗口暂停/恢复、命中 seek 不新建连接、未命中 seek 只重启一次、
  慢建连不重试、截断后续读、过期链接刷新、关闭清理。
- 验收指标（同一文件、新链接、同网络）：
  - 播放期间回源连接数峰值 ≤ 2；
  - `phase=connect` 连续超过 20 秒的次数为 0；
  - 任意 seek 到已缓存块的首字节耗时为 0（无回源请求）；
  - 连续播放 10 分钟无“等待数据”。

## 6. 风险

- 单连接吞吐不足：先用 1 条主流；若实测低于码率，再在同一流上做“分段续传”
  （仍复用连接），不回到多连接并发。
- 探针与主流同时建连仍可能被 CDN 限速：探针只在头部/moov 阶段使用，且 ≤4 MiB；
  若仍受限，退化为“先探针、后主流”的串行启动。
